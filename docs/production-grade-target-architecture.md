# PKAS 本地 AI 能力中台——生产级目标架构

状态：目标设计，不代表全部功能已实现
日期：2026-08-28
项目根：当前克隆目录（下文以 `$repoRoot` 表示）

## 1. 设计目标

PKAS 面向单个个人或单台电脑，但采用工业级的数据正确性、检索质量、证据链、故障降级、可观测性和可复制部署标准。它是客户端无关的本地 AI 能力中台：Codex 是首个适配器，其他支持 MCP、REST 或 OpenAI-compatible API 的客户端共享同一套知识、向量、Agent、工作流和审计能力。它不追求互联网超大规模并发，也不引入没有实际收益的微服务、Kubernetes、Kafka 或多节点数据库。

最高优先级依次为：

1. 不篡改、不丢失原始资料。
2. 不把助手声明、用户意图或 AI 推断混成已验证事实。
3. 检索结果可定位、可解释、可判断是否足够。
4. 云端模型或向量库故障时仍能完成本地精确检索。
5. 只处理变化数据，控制延迟、费用和重复劳动。
6. 能够打包复制到另一台 Windows 电脑，并通过同一套验收。
7. 客户端可以替换，知识资产、Agent 和工作流不能绑定在某一个客户端里。
8. 所有客户端配置变更必须经过解析校验、脱敏备份、原子写入、连接测试和一键回滚。

## 2. 最终运行形态

```text
Codex / 其他 AI 客户端 / IDE / 自研应用 / Web / CLI
                          │
                Integration Gateway
             MCP / REST / OpenAI API / SDK
                          │
                 Client Adapter SPI
       Codex Adapter / Generic MCP / Future Adapters
                          │
                   PKAS Core Runtime
       ┌──────────────┬──────────────┬──────────────┐
       │              │              │              │
 Capability Registry  Knowledge/RAG  Agent/Workflow Policy/Audit
       │              │              │              │
 Skill/MCP/Profiles  SQLite/FTS5    LangGraph      Approval
 Client Config       Qdrant         DeepSeek       Receipts
```

PKAS Core 是模块化单体和唯一后台状态拥有者。MCP、REST、OpenAI-compatible API、CLI 和各客户端配置适配器都是端口层，不直接拥有知识、任务或模型预算。Codex Adapter 只负责安全发现 `config.toml`、Skill 目录、MCP 配置和任务上下文；移除 Codex Adapter 不影响知识库和其他客户端。

### 2.1 模块边界

| 模块 | 责任 | 禁止承担 |
|---|---|---|
| Capability Registry | 统一登记客户端、Skill、MCP、接口、服务、版本和健康状态 | 直接执行不可信工具 |
| Client Adapter SPI | 检测客户端、解析/渲染配置、生成差异、测试连接 | 读写知识库正文 |
| Integration Gateway | 对外暴露 MCP、REST、OpenAI-compatible API 和 SDK 合约 | 保存客户端专属状态 |
| Knowledge & RAG | 原件、解析、FTS、向量、重排、引用和评测 | 修改客户端配置 |
| Agent Runtime | 有界规划、工具选择、预算、恢复和结构化结果 | 确定性同步和索引任务 |
| Workflow Engine | 定时同步、批处理、审批和可恢复步骤 | 隐藏第二次 LLM 推理 |
| Policy & Audit | 权限、秘密引用、审批、回执、备份和回滚 | 在日志中保存秘密值 |

### 2.2 Skill、MCP 与客户端配置事务

未来任何安装、启停、复制或配置写入统一走一条事务链：

```text
发现 → 规范化 → 权限/风险检查 → 生成差异 → 用户确认
    → 脱敏备份 → 临时文件写入 → 语法校验 → 原子替换
    → 客户端/MCP 连接测试 → 成功回执；失败自动回滚
```

- Skill 是带来源、版本、哈希、权限声明和资源清单的能力包，不只是一个 Markdown 文件。
- MCP Server 是可运行依赖，必须登记 transport、启动方式、健康状态、工具清单、权限和审计策略。
- Profile 把一组 Skill、MCP 工具、知识域和预算分配给一个项目或客户端；客户端只看到当前 Profile 允许的最小工具集合。
- 秘密只保存到 Windows Credential Manager/DPAPI 抽象后的 Secret Store；配置文件只保存秘密引用。
- Git 来源默认只读；更新必须显示版本差异和许可证，不自动执行仓库脚本。

### 2.3 管理台信息架构

本地管理台保持一个产品、一个导航和统一状态模型：

1. 总览：运行健康、待处理事项、成本和最近活动。
2. 能力中心：客户端、Skill、MCP、Profiles、安装来源和版本。
3. MCP 实验台：initialize、tools/resources/prompts 列表、Schema 检查、调用、重放和审计。
4. 知识中心：数据源、解析、全文库、向量库、覆盖率、失败重试。
5. RAG 实验室：查询链、召回、重排、引用、黄金集和回归门禁。
6. Agent 与工作流：任务图、预算、审批、失败恢复和证据回执。
7. 客户端接入：Codex 首先完成，其他客户端通过 Adapter SPI 增加。
8. 系统：秘密、备份、恢复、更新、许可证和审计。

当前已完成能力发现、三客户端配置事务内核和 Profile 后端：能够安全读取客户端 Skill/MCP 元数据，使用 Profile 保存客户端、能力、知识域、隐私范围和预算组合，并以脱敏预览、DPAPI备份、原子写入和失败回滚管理配置。真实客户端启用、Profile 编辑 UI 和运行时权限强制执行仍属于后续验收，不能因后端存在而视为已上线。

## 3. 数据分层

### 3.1 原件层 Source Vault

- 用户资料按 SHA-256 保存不可变原件，导入后重新计算哈希。
- 原始路径、文件名、大小、修改时间、来源连接器和导入授权范围单独登记。
- 原件、派生文本、向量、事实、推断和训练候选分目录、分表保存。
- 删除或替换派生数据不能影响原件；原件删除需要单独确认。

### 3.2 规范文档层

统一数据结构：

```text
Source → Document → Block → Chunk
```

- `Document`：一份文件、一次聊天导出或一个明确来源。
- `Block`：页面、章节、表格、代码符号、幻灯片、消息组或图像区域。
- `Chunk`：用于检索的最小完整语义单元，保留父 Block 和来源定位。
- 每层保存解析器版本、质量分、时间、领域、隐私、内容哈希和警告。

### 3.3 事实与观察层

- `WorkFact`：实际做过的工作、需求变化、采用的技术决策、验证结果和遗留事项。
- `EvidenceReceipt`：Git、测试、构建、部署、文件哈希、外部回执等独立证据。
- `Lesson`：成功经验、失败原因、适用范围和反例。
- `Observation`：客户特点、性格、意图、行为规律等可能出错的 AI 推断。
- Observation 永远不能覆盖 Fact；低置信度推断不能作为 Agent 行动依据。

## 4. 文档解析标准

解析采用“原生精确解析优先，视觉补全按需触发”：

1. 原生层读取 PDF 文字块、Word 段落/表格、Excel 单元格/公式、PPT 页面、代码符号和 JSON 字段。
2. 结构层恢复标题层级、页码、表格关系、批注、备注、坐标和阅读顺序。
3. 质量门判断是否缺页、乱码、文字过少、表格断裂或图片占比过高。
4. 只有不足页面进入 OCR/视觉解析；不能默认整份文档重复送云端。
5. 原生结果与 OCR 结果按坐标和内容哈希融合，不以 OCR 覆盖可靠原文。

切片规则按内容类型选择：

| 类型 | 主要边界 | 目标大小 | 特殊处理 |
|---|---|---:|---|
| 普通文档 | 标题、段落、页面 | 300–900 中文字 | 保留父章节摘要 |
| 表格 | 表头 + 行组 | 5–30 行 | 每块重复必要表头 |
| 代码 | 类、函数、配置段 | 40–200 行 | 保存符号名和路径 |
| 微信聊天 | 主题、时间窗口、回复链 | 5–30 条消息 | 保留说话人、时间和引用关系 |
| 截图 | OCR 区域、气泡顺序 | 1 个主题区域 | 保存图片哈希和坐标 |

不使用固定字符数作为唯一切片规则。父子块同时保留：小块负责召回，大块负责交给 Codex 阅读。

## 5. 索引一致性

SQLite 是正式元数据和状态源，FTS5 与 Qdrant 都是可重建索引。入库事务写入 `index_outbox`：

```text
SQLite 提交 Source/Document/Block/Chunk
                    ↓
             index_outbox 待处理
                    ↓
         FTS5 完成 + Qdrant 完成
                    ↓
          标记索引版本和覆盖率
```

任何一步失败都保留可重试状态，不允许出现“SQLite 已更新但系统假装向量也已更新”。索引幂等键由 `chunk_id + content_hash + embedding_model + chunker_version` 组成。

Qdrant Payload 只保存检索过滤和来源定位所需字段；正文以 SQLite 为准，搜索后按 `chunk_id` 回读，避免出现第二份不可控事实源。需要建立 Payload Index 的字段：

- `domain`
- `privacy`
- `source_type`
- `document_id`
- `event_time`
- `status`
- `embedding_version`

## 6. 高标准混合 RAG

### 6.1 默认检索链

```text
查询规范化
  ↓
精确实体/路径识别
  ↓
FTS5 Top 40 + Dense Vector Top 40
  ↓
元数据过滤
  ↓
RRF 融合
  ↓
候选去重与文档多样化
  ↓
按需 Rerank Top 20
  ↓
证据充分性与冲突检查
  ↓
返回 5–8 个父子来源片段
```

- 文件名、型号、函数名、客户称呼、报错文本优先精确检索。
- 自然语言、同义表达和跨文档问题使用向量召回。
- RRF 不直接混加 BM25 与余弦原始分数，避免分值尺度不同导致偏置。
- 只有候选接近、问题复杂或高价值任务才调用云端重排器。
- 多跳问题由 Agent 拆成有限子查询；普通问题禁止为了“智能”而调用 Agent。

### 6.2 检索健康状态

每次检索内部产生：

- 索引覆盖率和最新同步时间；
- FTS、vector、rerank 各通道命中数；
- 最高/最低相关度和来源多样性；
- 是否只有用户请求、AI 推断、过期资料或低质量 OCR；
- 证据是否足以回答，是否存在冲突。

正常检索静默。只有无结果、低相关、索引覆盖不足、信息冲突、来源过期、OCR 质量差、只有推断或云服务降级时才通知用户。

## 7. Agent 边界

Agent 只用于确定性代码难以可靠完成的任务：

1. 多跳问题的查询拆解和停止判断。
2. 交付完成后的工作事实、经验和候选观察提取。
3. 多来源冲突综合并明确列出证据差异。
4. 客户长期需求、承诺、风险和沟通模式的候选挖掘。

同步、哈希、解析、切片、去重、索引、备份和状态迁移全部使用确定性代码。Agent 的工具保持少而稳定：

- `search_context`
- `read_context_source`
- `inspect_project_state`
- `save_work_facts`
- `save_observation_candidate`

LangGraph 保存节点状态、重试和恢复；DeepSeek 只负责需要自然语言判断的节点。所有写回先通过证据、类型和置信度校验。

## 8. 可量化验收标准

### 数据正确性

- 原件导入后哈希一致率：100%。
- 每个检索片段可定位到 Source/Document/Block：100%。
- 重复同步幂等率：100%。
- 密钥进入源码、日志、知识库或检索结果：0。
- 助手声明被当作独立完成证据：0。

### 解析质量

- 原生文本保留率：≥99%。
- 关键字段召回率：≥95%。
- 表格表头与单元格关系保留率：≥98%。
- 高质量扫描件 OCR 字符准确率：≥95%。
- 解析失败、缺页和低质量页面漏报率：≤1%。

### 检索质量

- 建立不少于 150 条真实问题的黄金评测集，覆盖业务、项目、客户、聊天、代码、表格、图片和跨文档问题。
- Recall@10：≥90%。
- Precision@5：≥80%。
- MRR@10：≥0.85。
- 来源引用正确率：100%。
- restricted 越权召回：0。
- 低质量或证据不足却不报警：≤2%。

### 性能与降级

- 本机 FTS P95：≤300 ms。
- 云端查询向量 + 本机混合召回 P95：≤2.5 s。
- 启用重排的复杂检索 P95：≤5 s。
- 新增资料在一次同步触发后 5 分钟内进入双索引。
- Embedding/DeepSeek/Qdrant 任一不可用时，FTS 和来源阅读仍可用。

这些目标需要在目标电脑和真实评测集上测量；代码存在或单次成功不能替代验收数据。

## 9. 成本与容量

- Embedding 只处理新增或内容哈希变化的 Chunk；查询向量可短时缓存。
- 默认每批有上限、可恢复，并记录成功数、失败数、待处理数和调用量。
- Rerank 只处理 Top 20 左右候选，不对全库运行。
- DeepSeek 只参与复杂检索和交付后提炼，使用日预算、任务预算和结果缓存。
- 1024 维不会限制资料条数；容量主要由 Chunk 数量、Payload、HNSW 和原文规模决定。
- 达到几十万向量并出现内存压力后，再依据评测启用 on-disk、量化或冷热集合；不能提前牺牲召回率。

## 10. 运行、备份和复制

正式安装包包含：

- Python 运行时和锁定依赖；
- PKAS Core Windows 后台服务；
- Qdrant 固定版本二进制；
- Web 管理台；
- 初始化、升级、健康检查、备份和恢复命令；
- 空白配置模板和 DPAPI 密钥输入入口；
- 不包含任何用户资料、密钥或现有数据库。

备份分三层：

1. SQLite 在线一致性备份和完整性检查。
2. 原件库增量备份和哈希清单。
3. Qdrant Snapshot 或直接重建方案。

数据库迁移必须版本化并可回滚；向量模型升级使用新集合 + 别名切换，完成评测后再停用旧集合，不能原地混用不同维度或模型的向量。

## 11. 当前实际状态与主要差距

当前已经具备：SQLite/FTS5、原件与来源定位、正式 Block/typed Child Chunk、Qdrant 1.19.0、SiliconFlow `BAAI/bge-m3`、RRF、来源多样化、按需 `BAAI/bge-reranker-v2-m3`、本地与重排的等权倒数排名融合、结构化检索健康、最小 Qdrant Payload、事务化索引 Outbox、单实例 Core Worker、降级检索、真实向量图和 150 题来源绑定评测池。

尚未达到本设计标准的重点：

1. Core、Dashboard、Qdrant、Knowledge Sync 与 Daily Backup 的安装和精确卸载能力已实现并曾完成本机隔离验收；但用户已于 2026-08-28 撤销当前电脑的自启动授权，现有 `PKAS-*` 任务和相关常驻进程均应保持不存在。策略缺失或不为显式 `true` 时安装脚本必须拒绝注册任务；MCP同样保持关闭。现有实现仍是进程内创建 Core 组件，不是纯薄客户端。
2. 已有事务化 `index_outbox`、失败退避、陈旧任务恢复、强制终止恢复实演和 100% 向量覆盖；仍需真实断电和更长期运行观测。
3. 已建立正式 Block/父子/类型化切片；代码还需从连续行块升级到 AST 符号边界，聊天还需从消息窗口升级到主题/回复链。
4. 已有 Rerank、来源多样化和基础充分性判断，但仍缺跨来源事实冲突检测。
5. 150 题池、人工复核队列、未召回来源补审和严格 human 门禁已经建立，但按 `graded-scope-v2` 协议正式可用题仍为 0；必须由用户逐题完成 0–3 级判断，旧 7 题也不能沿用不完整 Precision。
6. 已有无个人数据导出包、锁定依赖、Qdrant 哈希安装、路径独立任务、隔离验收和精确卸载；本机中文空格路径全链路已通过，但另一台物理电脑尚未复制安装验收。自动任务能力只代表可安装能力，不代表当前电脑获得持续运行授权。
7. 显式线程事实采集和交付后候选挖掘仍未完成。

当前可称为“本机个人知识库运行底座已上线、RAG 银标门禁可用”；在人工黄金集、另一台物理电脑复制和剩余知识治理差距通过前，不能称为完整生产上线。
