# 架构概览

```text
本机文件 / Obsidian / 授权导出的聊天记录
                    │
                    ▼
          来源发现与格式识别
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
 A：目录与全文索引       B：正文切片与向量索引
          │                   │
          └─────────┬─────────┘
                    ▼
            AB：检索融合与排序
                    │
          来源追溯、充分性和告警
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
       本地 API              MCP
          │                   │
          └───── AI 客户端 ───┘
```

## 设计原则

1. 原文件是事实来源，索引可以删除并重建。
2. A库与B库分开保存、分开测试，避免“有结果”掩盖某个通道失效。
3. AB只负责融合，不再复制一份知识。
4. 每条结果必须能够回到原文件或原始导出记录。
5. 文件发现、正文解析、向量化和AI摘要是不同阶段，可以分别开启。
6. 云端Embedding或模型处理必须由用户主动配置；关闭后仍可使用本地A检索。
7. 客户端只调用统一检索接口，Codex、MCP和管理台不各写一套搜索逻辑。

## 模块边界

- `sources`：扫描指定目录并记录来源状态。
- `parsers`：按格式抽取结构、正文和定位信息。
- `catalog`：文件名、路径、类型和全文关键词索引。
- `vectors`：Embedding生成、Qdrant写入和覆盖状态。
- `retrieval`：A、B、AB三种检索模式及融合排序。
- `connectors`：MCP、本地API、Obsidian和聊天导出适配器。
- `console`：导入、状态、检索测试、质量评测和运行管理。
